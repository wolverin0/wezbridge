# T-0602 — guard: recursive-delete of shared temp root + git stash ban

Covers: extending `src/catastrophic-commands.cjs` (consumed read-only by
`C:/Users/pauol/.claude/hooks/lane-guard.cjs`) to DENY (1) recursive deletes
that hit the shared scratch root `T:/claudecodetemp` (any spelling), the
shared `claude/` session dir and its direct children, or another session's
own scratchpad subtree, and (2) any mutating `git stash` form (push/save/
pop/apply/drop/clear/-u), while still allowing `git stash list|show`, deletes
inside the caller's own worktree/cwd or own scratchpad, and every existing
catastrophic-commands.test.cjs case (no regression).

Incident (24/09): a verifier ran `rm -rf /t/claudecodetemp` — the root of
every session's scratchpad, task outputs, and ad-hoc worktrees. 5 agents ran
`git stash` (stack shared across worktrees/sessions) despite a prose ban in
their briefs. Prose isn't enough → this is the enforcement artifact.

## Acceptance criteria

1. Fail-first: tests committed first (red), then implementation (green).
   Deny cases: `rm -rf /t/claudecodetemp`, `rm -rf T:/claudecodetemp/claude`,
   `Remove-Item -Recurse T:\claudecodetemp`, `git stash`,
   `git stash push -u -m x`, `git stash pop`, `rm -rf ~`, `rm -rf /`,
   chained `cd /t && rm -rf claudecodetemp`.
   Allow cases: `rm -rf <own scratchpad>/x` (session-scoped), `git stash
   list`, `rm -rf` inside the agent's own worktree/cwd, `git worktree
   remove`, `rm -rf node_modules` inside cwd.
2. No legit/existing command gets newly blocked: full existing
   `catastrophic-commands.test.cjs` suite stays green, plus spot checks
   against strings used by common worker flows (`git worktree remove
   --force`, `rm -rf "$TMPDIR/x"`).
3. Hook-consumption story documented: either the hook (`lane-guard.cjs`)
   needs no change beyond merging this module (state that + give a live
   check command), or a unified diff + apply/rollback + live-check
   procedure is produced at
   `_intel/briefs/2026-09-24-T0602-lane-guard.patch` (not applied by this
   worker — `C:/Users/pauol/.claude/` is operator-owned).

## Design: how the module learns "own scope"

`classifyCatastrophic(command, context)` gains an optional second arg
`context = { cwd, sessionId }`. `lane-guard.cjs`'s PreToolUse stdin payload
already carries `input.cwd` and `input.session_id` (confirmed: other hooks
in the same dir, e.g. `pane-beacon.cjs`, `orchestrator-autoload.cjs`,
`gitnexus-hook.cjs`, already read `input.cwd`/`input.session_id` from the
identical payload shape) — so the hook can pass
`{ cwd: input.cwd, sessionId: input.session_id }` without any new plumbing.
The classifier stays pure (no I/O): it only compares strings/paths already
handed to it.

- Own worktree/cwd: any resolved target path prefixed by `context.cwd` is
  in scope → allowed, checked first among the "allow" branches.
- Own scratchpad: the scratchpad layout is
  `T:/claudecodetemp/claude/<project-slug>/<session-id>/scratchpad/...`. The
  project-slug's exact mangling algorithm is not reimplemented — instead the
  guard matches `.../claude/<any-one-segment>/<context.sessionId>(/...)?`,
  which pins the match on the session id the hook already knows, independent
  of slug format.
- If `context` (cwd/sessionId) is missing/undeterminable, the guard still
  denies the explicit dangerous roots (temp root itself, the shared
  `claude/` dir and its direct children, filesystem/drive roots, bare `~`)
  but does NOT block `rm -r` generally — satisfies "don't block all rm -r"
  from the brief.

## Hook patch — apply / rollback / live-check

Merging `src/catastrophic-commands.cjs` alone is NOT enough for full
protection: `lane-guard.cjs` currently calls `classify(cmdC)` with no
context, so the module falls back to its conservative mode (explicit
dangerous roots only — temp root, shared `claude/` dir + direct children,
`~`, drive roots — still denied; deep `claude/<slug>/<session>/...` paths
and the caller's own worktree/scratchpad are NOT distinguished from each
other, so today's git-stash-ban part works immediately on merge, but the
recursive-delete guard only reaches its full "protect others' sessions,
allow my own" behavior once the hook passes `{ cwd, sessionId }`). The
one-line patch is at `_intel/briefs/2026-09-24-T0602-lane-guard.patch`
(paths relative to `C:/Users/pauol/.claude`).

```bash
  | WEZ_LANE=wezbridge node "C:/Users/pauol/.claude/hooks/lane-guard.cjs"

```
