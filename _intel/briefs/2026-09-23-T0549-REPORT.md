# T-0549 report — codex_worker.py + multi_agent_v2 verification (2026-09-23)

Card: `_intel/tasks/T-0549.json`. Context: `wezbridge/_intel/briefs/2026-09-23-delegation-enforcement-MEMO.md`,

## Deliverable

`wezbridge/scripts/orchestration/codex_worker.py` — single dispatch point for Codex workers.
Validates `(model, effort)` against `_intel/model-tiers.json`'s codex-runtime entries (falls
back to a hardcoded table if that file is missing/unreadable), builds and runs:

```
codex exec -m <model> -c model_reasoning_effort=<effort> -s workspace-write --cd <cwd>
           --skip-git-repo-check --json -o <last-message-file> "<mission prompt>"
```

captures stdout/stderr to `_intel/foreman/<task>-codex.log`, parses the `[WORKER_DONE]`
closure by reusing `foreman.find_worker_done` (same closure grammar as the orca-terminal
dispatch path in `task_router.py`), and prints one JSON result line. Exits non-zero when the
model/effort pair is invalid (no subprocess spawned), the child times out, or no closure is
found.

Two bugs found and fixed while getting a real `codex exec` call to run, both now baked into
the wrapper:
- **PATHEXT / WinError 2**: `codex` is installed as `codex.cmd`; `subprocess.run(shell=False)`
  on Windows does not resolve that, so a bare `"codex"` argv0 fails immediately. Fixed with
  `shutil.which()`.
- **"Not inside a trusted directory"**: worker cwds are frequently a fresh temp dir or
  worktree not yet in `~/.codex/config.toml`'s `[projects.*]` trust list. Fixed by always
  passing `--skip-git-repo-check`.
- Also pinned `stdin=subprocess.DEVNULL` on the child — without it, the child printed
  "Reading additional input from stdin..." and appended the parent's inherited stdin as a
  `<stdin>` block, which is not what a scripted, non-interactive dispatch wants.

## Live checks (budget: at most 4 real `codex exec` runs — used exactly 4)

1. `codex_worker.py --model gpt-6-luna --effort low` on a trivial brief, pre-fix (`workspace-write`,
   no `--skip-git-repo-check`) → failed fast on "Not inside a trusted directory" (the bug above).
2. Raw `codex exec -m gpt-6-luna -s read-only --enable multi_agent_v2 --skip-git-repo-check` →
   returned in ~5s with a **real API 400**:
   `{"type":"error","status":400,"error":{"type":"invalid_request_error","message":"The 'gpt-6-luna' model is not supported when using Codex with a ChatGPT account."}}`
3. `codex_worker.py --model gpt-6-luna --effort low` post-fix (`workspace-write`) → hung past
   its 180s timeout (killed manually after ~5 min via `TaskStop`, no log line ever written).
   Given run 2 got the same model rejected in 5s under `-s read-only`, the hang is most likely
   contention from the other `codex.exe`/`codex-windows-sandbox-set` processes already running
   on this machine (3 other Codex panes were live at the time), not a wrapper bug — but this
   is not confirmed, and it means `-s workspace-write` latency/hang risk under contention is an
   open item, not disproven.
4. Raw `codex exec -m gpt-6-sol -s workspace-write --skip-git-repo-check` → returned in ~5s,
   same shape: `"The 'gpt-6-sol' model is not supported when using Codex with a ChatGPT account."`

**Conclusion: neither `gpt-6-sol` nor `gpt-6-luna` is currently usable through this machine's
ChatGPT-account Codex auth, independent of the wrapper.** `_intel/model-tiers.json` and the
2026-09-23 crosscheck memo list both as available Codex-runtime models; that is not yet true
for ChatGPT-plan auth as of this run. Only `gpt-6-astra` is confirmed live-usable (it is the
operator's current interactive default per `~/.codex/config.toml`'s top-level `model` key and
appears in `models_cache.json` and `[tui.model_availability_nux]`). No 5th run was made to stay
inside the stated budget; a follow-up run with `gpt-6-astra` would fully close AC1's *mechanism*
(a real `[WORKER_DONE]` closure through the wrapper) even though AC1 as written names
`gpt-6-luna` specifically.

### multi_agent_v2

Not found via a live web check (out of scope this run); found instead in the **local**
`codex-security` plugin at
`C:/Users/pauol/.codex/.tmp/plugins/plugins/codex-security/references/config-preflight.md`
and `.../scripts/config_preflight.py`, which document the real config shape:

- Accepts either `[features] multi_agent_v2 = true` or `[features.multi_agent_v2] enabled = true`.
- Is Codex's **V2** multi-agent runtime, distinct from the **V1** runtime this machine currently
  runs (`~/.codex/config.toml` has `[features] multi_agent = true` and
  `[agents] max_concurrent_threads_per_session = 2`, `default_subagent_model = "gpt-5.6-luna"`,
  `default_subagent_reasoning_effort = "high"` — all V1 keys).
- V2 **cannot be combined with `agents.max_threads`**; `agents.max_depth` is V1-only.
- V2's own session cap lives at `features.multi_agent_v2.max_concurrent_threads_per_session`
  (documented default `4`), a different key from V1's `agents.max_concurrent_threads_per_session`.

**Not verified**: whether V2 actually fixes the community-reported "children silently inherit
parent model+effort" bug (the memo's open item). Testing that needs (a) a model this account
can use for both parent and child — only `gpt-6-astra` qualifies right now — and (b) a way to
observe a child's actual `turn_context`, which `codex exec` (single-shot, non-interactive) may
not expose for an in-process spawn at all; subagent spawning looks like a TUI/`codex agents`
concept, not an `exec` one. This needs a dedicated follow-up run, explicitly out of today's
4-run budget.
